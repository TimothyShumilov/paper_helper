# Отчёт об изменениях MVP

В данном документе описаны все отклонения и исправления, внесённые в реализацию MVP относительно первоначального дизайна, зафиксированного в `design_doc.md`.

---

## 1. Инфраструктура: Qdrant healthcheck

**Файл:** `docker-compose.yml`

**Проблема.** Образ `qdrant/qdrant:v1.9.2` не содержит утилиту `curl`. Стандартная проверка доступности сервиса через `curl http://localhost:6333/healthz` завершалась с ошибкой `curl not found`, из-за чего контейнер бесконечно оставался в состоянии `unhealthy` и бот не запускался.

**Решение.** Healthcheck заменён на проверку TCP-соединения средствами самого `bash`:

```yaml
test: ["CMD-SHELL", "bash -c '</dev/tcp/localhost/6333' 2>/dev/null"]
```

## 2. Embedding-модель: исправление имени GGUF-файла

**Файлы:** `config.py`, `.env.example`

**Проблема.** Изначально имя файла было указано в смешанном регистре: `Qwen3-Embedding-0.6B-Q4_K_M.gguf`. В HuggingFace-репозитории файл хранится в нижнем регистре, что приводило к ошибке HTTP 404 при попытке скачать модель.

**Решение.** Имя файла приведено к нижнему регистру:

```
qwen3-embedding-0.6b-q4_k_m.gguf
```

---

## 3. Embedding-модель: обновление llama-cpp-python

**Файл:** `requirements.txt`

**Проблема.** Версия `llama-cpp-python==0.2.90` вышла раньше, чем в llama.cpp появилась поддержка архитектуры Qwen3. При попытке загрузить GGUF-файл выбрасывалось исключение:

```
ValueError: Failed to load model from file: qwen3-embedding-0.6b-q4_k_m.gguf
```

**Решение.** Версия библиотеки обновлена до `0.3.16`, которая поддерживает Qwen3.

---

## 4. LLM API: замена OpenRouter на Groq

**Файлы:** `core/rag_pipeline.py`, `config.py`, `requirements.txt`, `.env.example`

**Проблема.** Design doc предполагал использование OpenRouter с моделью **Qwen3 VL 235B A22B Thinking**. При интеграции бесплатный тир OpenRouter систематически отвечал кодом `429 Too Many Requests` даже при единичных запросах, что делало API непригодным для MVP.

**Решение.** OpenRouter полностью заменён на **Groq API** с моделью `llama-3.3-70b-versatile`:

- `httpx`-клиент с ручными HTTP-запросами заменён на официальный SDK `groq==0.13.1` (`AsyncGroq`).
- Переменные окружения `OPENROUTER_API_KEY` / `OPENROUTER_MODEL` заменены на `GROQ_API_KEY` / `GROQ_MODEL`.
- Бесплатный тир Groq предоставляет существенно более высокие лимиты для тестирования и прототипирования.

## 5. Суммаризация длинных статей: map-reduce

**Файл:** `core/rag_pipeline.py`

**Проблема.** Groq ограничивает входной контекст в рамках тарифного плана (~12 000 токенов в минуту). При суммаризации крупных статей (более ~60 страниц) общий объём чанков превышал лимит, что вызывало ошибку `HTTP 413 Request Entity Too Large`.

**Решение.** Реализована суммаризация по принципу **map-reduce**:

1. Функция `_batch_chunks()` разбивает список чанков на группы, не превышающие `SUMMARIZE_BATCH_CHAR_LIMIT = 24 000` символов.
2. Каждая группа суммаризируется отдельным вызовом LLM (map-фаза).
3. Полученные частичные summary объединяются и подаются на финальный вызов LLM для создания итогового краткого изложения (reduce-фаза).

## 6. Исправление PTB ConversationHandler: `allow_reentry`

**Файл:** `bot/handlers.py`

**Проблема.** В `ConversationHandler` был выставлен флаг `allow_reentry=True`. Этот флаг заставляет python-telegram-bot проверять `entry_points` перед обработчиками текущего состояния при каждом апдейте. В результате текстовые сообщения в состоянии `READY` попадали в `arxiv_id_handler` (entry point) вместо `question_handler`, и бот отвечал «Не могу распознать ID статьи» на любой вопрос пользователя.

**Решение.** Флаг `allow_reentry=True` удалён.

## 7. UX: замена inline action-кнопок на команды бота

**Файлы:** `bot/handlers.py`, `bot/keyboards.py`

**Проблема/пожелание.** Design doc предполагал наличие inline-кнопок «Суммаризировать» и «Завершить сессию» под сообщениями бота. На практике постоянные кнопки под каждым сообщением перегружали интерфейс чата.

**Решение.** Inline action-кнопки убраны. Вместо них реализованы **команды бота**, зарегистрированные через `BotCommand` + `set_my_commands` (отображаются в меню команд Telegram):

| Команда | Действие |
|---|---|
| `/start` | Начать / проверить активную сессию |
| `/summarize` | Суммаризировать текущую статью |
| `/new` | Завершить сессию и выбрать следующую |

Рейтинговые кнопки (👍/👎) и кнопки навигации по сессиям остались inline — у них есть payload и они показываются ситуативно.

## 8. UX: /new как переключатель сессий с рейтингом и пагинацией

**Файлы:** `bot/handlers.py`, `bot/keyboards.py`

**Изменение.** Design doc предполагал отдельную кнопку «Завершить сессию» и список из последних 5 сессий без пагинации для возврата. В реализации поведение объединено в одну команду `/new` с расширенной функциональностью.

**Поведение `/new`:**

- **При наличии активной сессии:** завершает текущую сессию в БД, показывает рейтинговые кнопки (👍 / 👎) с просьбой оценить работу бота. После оценки отображается список доступных сессий.
- **При отсутствии активной сессии:** сразу показывает список доступных сессий.

**Список сессий:**

- Отображается с пагинацией: по 5 сессий на страницу.
- Навигация кнопками «← Назад» / «Вперёд →» (отображаются только при наличии соседних страниц).
- Callback для навигации: `action:sessions:page:{n}`.
- При выборе сессии со статусом `ended` — сессия реактивируется в БД.
- Пользователь может не выбирать сессию из списка и вместо этого отправить ID новой статьи.
